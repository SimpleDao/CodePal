## 4. 责任链 (Chain of Responsibility) 模式分析

ChatPanel 中实际存在 **三层** 责任链模式，虽然不是标准的 GoF `Handler` 接口实现，但其核心思想（请求沿链传递，每个节点决定处理或放行）贯穿了整个工具执行体系。

### 4.1 第一层：onToolCalls 工具类型分类链

这是 ChatPanel 中最核心的责任链，位于 `createStreamCallback().onToolCalls()` (L1665-L2072)。

```
模型返回 tool_calls[]
  │
  └── 第一遍遍历 (逐个工具分类，Link-1)
      │
      ├── edit_file / write_file / create_new_file?
      │   ├─ YES → 按 filePath 分组收集 (Link-1 处理)
      │   │       不立即执行，留到第二遍统一处理
      │   └─ NO  → 传递给下一个处理器
      │
      ├── todo?
      │   ├─ YES → handleTodoTool(tc)              (Link-2 处理)
      │   │        addMsgToConversation + saveToDb
      │   └─ NO  → 传递给下一个处理器
      │
      ├── search_project?
      │   ├─ YES → SearchAgent.search()            (Link-3 处理)
      │   │        进度回调 → ChatWebView 实时更新工具卡片
      │   │        addMsgToConversation + saveToDb
      │   └─ NO  → 传递给下一个处理器
      │
      ├── read_chat_history?
      │   ├─ YES → handleReadChatHistory(tc)       (Link-4 处理)
      │   │        DBChatHistoryRepository 查询历史
      │   │        addMsgToConversation + saveToDb
      │   └─ NO  → 传递给下一个处理器
      │
      └── 默认处理器 (Link-5 Fallback)
          ├─ McpService.isMcpTool(name)?
          │   └─ McpService.executeTool(name, args)
          └─ 否则:
              └─ ToolExecutor.execute(tc, project, craftMode)
              └─ addMsgToConversation + saveToDb + 更新工具卡片
  │
  └── 第二遍遍历 (文件编辑工具统一处理)
      │
      ├── Craft 模式 → 对所有收集的 edit_file/write_file 组:
      │   ├─ write_file → FileOperationService.writeFile()
      │   ├─ edit_file → ToolExecutor.applyEdits(original, editPairs)
      │   │               └─ 三级匹配链: 精确匹配 → 柔性匹配 → 正则匹配
      │   └─ create_new_file → FileOperationService.writeFile()
      │   └─ VFS 刷新 → sendToApi() (循环继续)
      │
      └── Plan 模式 → 拒绝所有文件修改
          └─ 返回错误信息 → sendToApi() (循环继续)
```

**关键特征：**
- 链节按优先级有序排列，高优先级的工具类型先处理
- `edit_file/write_file` 被**收集但不立即执行**，体现了责任链中的**延迟处理**策略
- 默认处理器 (`ToolExecutor.execute`) 作为链的末端，捕获所有未被上层处理的工具
- 链没有显式的 `nextHandler` 字段，而是通过 `if-else` 顺序判断隐式实现

### 4.2 第二层：ToolExecutor.execute() 命令分发链

虽然 `ToolExecutor` 使用 `switch-case` 而非责任链接口，但其 `execRunCommand()` 方法内部实现了**三级命令分类链** (L613-L705)：

```
execRunCommand(command)
  │
  ├── Link-1: isFileWritingCommand(command)?
  │   └─ YES → 直接拦截，禁止执行 → 返回错误引导使用文件工具
  │
  ├── Link-2: isFileDeletingCommand(command)?
  │   └─ YES → 直接拦截，禁止执行 → 返回错误引导使用 delete_file
  │
  ├── Link-3: CommandClassifier.classify(command)
  │   ├─ DANGEROUS   → 弹确认 (不可加入信任名单)
  │   ├─ CONSOLE     → 弹确认 (可加入信任名单)
  │   ├─ READ_ONLY   → 静默执行 CommandRunner.execute()
  │   └─ DEFAULT     → 静默执行
  │
  └── Link-4: 信任名单检查
      └─ confirmProvider.isTrusted(command)? → 跳过确认直接执行
```

### 4.3 第三层：applyEdits 三级编辑匹配链

`ToolExecutor.applyEdits()` → `applySingleEdit()` (L144-L171) 实现了编辑文本的**三级回退匹配链**：

```
applySingleEdit(work, search, replace)
  │
  ├── 精确匹配 (精确逐字符匹配，容忍CRLF/LF差异)
  │   ├─ 1处命中 → 成功返回
  │   └─ >1处命中 / 0命中 → 进入下一级
  │
  ├── 柔性匹配 (逐行trim后滑动窗口比较，容忍缩进/空格差异)
  │   ├─ 1处命中 → 保留首行缩进，回填replace
  │   └─ >1处命中 / 0命中 → 进入下一级
  │
  └── 正则匹配 (分词后用 \s* 连接，容忍任意空白)
      ├─ 1处命中 → 保留原缩进，替换
      └─ 0命中 / >1命中 → 返回错误
```

### 4.4 责任链的优缺点分析

| 优点 | 缺点 |
|------|------|
| 每个工具类型有独立处理逻辑，新增工具只需在链中添加判断 | 链节顺序硬编码，调整优先级需改源码 |
| `edit_file` 的延迟处理 + 合并策略避免重复写盘 | 没有显式的 `Handler` 接口，难以单元测试单个链节 |
| 三级编辑匹配链优雅处理了 AI 生成的不完美编辑 | 链节间通过 `currentSessionId`、`project` 等全局状态通信 |
| Fallback 处理器兜底，未识别的工具不会丢失 | 链的长度随工具类型增加线性增长 |

### 4.5 建议改进：标准化责任链接口

当前隐式责任链可以重构为显式模式：

```java
// 建议的标准 Handler 接口
interface ToolCallHandler {
    /**
     * @return true=已处理，停止传递；false=未处理，传递给下一个
     */
    boolean handle(ToolCall tc, HandlerContext ctx);
    void setNext(ToolCallHandler next);
}

// 各 Handler 实现
class TodoHandler implements ToolCallHandler { ... }
class SearchProjectHandler implements ToolCallHandler { ... }
class ReadChatHistoryHandler implements ToolCallHandler { ... }
class DefaultToolHandler implements ToolCallHandler { ... }
class FileEditHandler implements ToolCallHandler { ... }  // 第二遍处理

// 使用
ToolCallHandler chain = new TodoHandler();
chain.setNext(new SearchProjectHandler());
chain.getNext().setNext(new ReadChatHistoryHandler());
chain.getNext().getNext().setNext(new DefaultToolHandler());
```

## 12. 流式代数机制 (Stream Generation)

防止旧回调污染的安全机制：

```
sendToApi() 时: streamGeneration++ (递增代数)
每次回调中:   if (streamGeneration != myGen) return;  // 代数不匹配则丢弃

场景:
  1. 用户点击停止 → streamGeneration++ → 旧SSE事件全部被忽略
  2. 快速连续发送 → 每个sendToApi()自带新代数 → 旧请求回调自动失效
  3. 工具轮次执行前检查 → streamGeneration != myGenFinal → break中止
```

# 第二部分：架构不足与逻辑问题分析

## 一、严重问题 (Critical)

### 1.1 `streamGeneration` 缺少 volatile → 多线程可见性 Bug

```java
// Line 295
private int streamGeneration = 0;  // ❌ 无 volatile
```

**读写线程：**
- **EDT 写入**：`sendMessage()` (L1217 `streamGeneration++`)、`sendToApi()` (L1387 `++streamGeneration`)
- **后台线程读取**：`executeOnPooledThread` 块 (L1436 `if (streamGeneration != myGen) return;`)

由于没有 `volatile`，后台线程可能永远看不到 EDT 上对 `streamGeneration` 的更新，导致本应失效的旧回调继续执行。虽然大多数后续检查在 `invokeLater` 中（走 EDT），但 **L1436 的检查直接在 `executeOnPooledThread` 的后台线程上执行**，存在确定的可见性风险。

**后果：** 用户点击停止后，旧工具回调可能仍然触发执行，产生幽灵文件修改。

### 1.2 `isReceiving` 无 volatile → 线程同步缺陷

```java
// Line 290
private boolean isReceiving = false;  // ❌ 无 volatile
```

- EDT 写入: `sendToApi()` L1386, `onAcpComplete()` L3655
- `handleAcpNotification` 中的 `invokeLater` 读取 L3426
- 未来如果任何非 EDT 路径调用，状态不可见

### 1.3 `sendToApi()` 超长调用 → 递归爆炸风险

```
sendToApi()
  → streamChat → onToolCalls → 执行工具 → sendToApi()
                                               → streamChat → onToolCalls → sendToApi()
                                                                                → ...
```

`sendToApi()` 在 **4个独立分支** 中自调用：
- L1865-1870: Plan 模式拒绝文件修改后重发
- L2041-2046: Craft 模式写盘完成后重发
- L2064-2071: 非编辑类工具执行后重发
- L2070: 工具发现分支的重发

**问题：** 没有任何调用深度计数器或最大递归限制。如果模型陷入工具调用循环（比如 run_command 编译失败 → 修改 → 再编译 → 再失败），`sendToApi()` 会无限自调用形成**逻辑递归（非栈递归，因为是异步回调），但每次都会消耗一轮 API token**，直到上下文窗口耗尽。

```java
}
```

`registerFileListener()` 和 `registerSelectionListener()` 通过 `project.getMessageBus().connect()` 注册订阅，但没有看到显式的 `disconnect()` 调用。如果 `ChatPanel` 被重新创建（例如工具窗口关闭再打开），旧的监听器仍然存活。

## 六、其他设计缺陷

### 6.1 原始类型使用

```java
// L235, L316 等
private java.util.Map<String, String[]> acpToolRecords  // String[] 丢失类型语义
```

`String[]` 的 `[0]=名称, [1]=结果` 没有类型安全。应该使用 `record ToolRecord(String name, String result)`。

### 6.2 魔法数字

```java
// L297
private static final long FULL_RENDER_INTERVAL_MS = 500;

// L384
private static final long acpContextWindowSize = 200_000L;

// L3874
private long getContextWindowLimit() { return 1_000_000; }

// L4412
DBChatHistoryRepository.getRecentMessages(sessionId, 50, 0) // 50是什么？
```

部分有常量（如 `FULL_RENDER_INTERVAL_MS`），但 `50`、`20`、`3000` 等散落的值没有语义化。

### 6.3 `parseArgs` 和 `getArgStr` 无异常处理

```java
// L1683-1684
JsonObject a = parseArgs(tc);
String filePath = getArgStr(a, "file_path", "");
```

如果 JSON 解析失败，`parseArgs` 返回 `null` → `getArgStr` 直接 NPE。虽然在 `onToolCalls` 的 try-catch 中有兜底，但 `parseArgs` 被多处独立调用（如 `search_project` 分支 L1703），没有统一防护。

### 6.4 异步任务的取消不彻底

```java
// L1217
streamGeneration++;  // 递增代数，使旧回调失效
```

这只是"逻辑取消"——旧的回调仍然会进入 EDT 队列执行，只是在第一行检查代数时被跳过。如果回调中包含重量级操作（如 Markdown 渲染），虽然最终被跳过，但之前可能的 JSON 解析、对象构建等已经白白执行。
