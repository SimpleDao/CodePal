# 项目文档实时同步（架构 + 业务表关系）

当你在为一个项目做开发（写代码、写 SQL、建表改表、做业务功能）时，必须**实时**维护项目文档：
`.codepal/architecture.md`（项目架构总账）、`.codepal/table-relations.md`（按表分组的业务关系）、
`.codepal/progress/` 目录（**一天一个文件**的工作流水）。
这些文档既给用户看，也是你自己跨会话的持久记忆——会话会被压缩、会开新会话，
但它们一直在项目里，**随手可查，查完即更新**。

## 文档的分工（别混）

| 文件 | 内容 | 写法 |
| --- | --- | --- |
| `.codepal/architecture.md` | 项目架构总账：业务背景、模块结构、技术栈、数据模型总览、进行中与遗留 | 按小节增量更新；重大重构才整体整理（整理前必须先读全文） |
| `.codepal/table-relations.md` | 按表分组的业务关系字典：每张业务表一节 | **只按表小节增量合并**，禁止整体重写 |
| `.codepal/progress/YYYY-MM-DD.md` | 当天的工作流水：修了什么 bug（现象/根因/修法）、定了什么方案、遗留什么 | **一天一文件**，append-only，每天几行提炼要点 |

文档放在**当前项目的 `.codepal/` 目录**——这是本插件的私有目录，不污染项目自身的 `docs/`；
随项目走，用户可在 IDE 项目树里直接打开查看。是否提交 git 由用户决定（见下方 git 纪律）。
首次创建用 `create_new_file`（会自动建父目录），并顺带告知用户文档位置；此后静默维护。

## 【重要】初始状态纪律：禁止为写文档而扫描项目

刚接入一个项目时，这些文档通常还不存在。此时你**只能**：

1. 用 `create_new_file` 创建 `architecture.md` 与 `table-relations.md` 两份**骨架文档**
   （只含标题、小节结构和占位说明，内容留空）；
   `.codepal/progress/` 目录不需要预建——首次写当天流水时由 `create_new_file` 自动产生；
2. 之后**只把当前任务中真实接触到的表/模块**渐进写入——做了什么就记什么；
3. **严格禁止**：为了"先把文档写全"而全量扫描项目源码、遍历所有文件、逐表探测数据库——
   这是浪费 token 的行为，明确不允许；
4. `SHOW TABLES` 这类轻量清单查询是允许的（用于知晓库里有哪些表），但**逐表** schema/抽样
   只限当前任务涉及的表；
5. 仅当**用户明确要求**「梳理整个项目的架构/所有表关系」时，才做系统性梳理：
   先用 `todo` 工具把梳理拆解成小步任务、控制范围，再分批执行，不要一口气扫完。

## 何时读（动手前）

满足任一条，先读再干：

1. 要写 SQL / 做业务改动 / 涉及数据库表 → 先 `search_tool` 在 `.codepal/table-relations.md` 里搜相关表名，
   并查看对应**实体类**（`view_file_outline` / `read_file_range`）确认字段与注释；
2. 需要项目整体结构、模块脉络、技术决策 → 读 `.codepal/architecture.md`；
3. 接手陌生项目 / 用户说「继续」→ 先读两份文档建立全局认知，再看最近 1~2 天的工作流水
   （`list_files` 列出 `.codepal/progress/` 下有哪些日期，`read_file_range` 读最近一两个文件）。

读取策略：**够用即止**。用 `read_file_range` 只读相关小节，不要每次全文拉取。

## 何时写（实时纪律，不是收尾才写）

1. **表关系发生变化或首次接触某张表**：写了 SQL、建了表、改了字段、通过 `query_database`
   查清了一张表的结构/关联/业务含义 → **当场**把该表小节写入 `.codepal/table-relations.md`
   （已记录且无变化的表不要重复写）；
2. **架构级变化**：新增模块、目录调整、技术选型、重大重构 → 当场更新 `.codepal/architecture.md` 对应小节；
3. **会话收尾**：本轮有实质进展（修了 bug / 定了方案 / 完成阶段）→ 把当天 2~5 行流水写入
   `.codepal/progress/YYYY-MM-DD.md`（当天的文件不存在就用 `create_new_file` 创建，已存在则
   `edit_file` 在文件末尾追加；格式见下）；无实质进展就不写；
4. **收尾自检**：本次改动涉及的表/模块是否都已同步到对应文档，漏了就补。

## `.codepal/progress/` 进度流水（跨会话的过程记忆，一天一文件）

- 文件名即日期：`.codepal/progress/2026-09-15.md`。**一天一文件**，避免单个文件随日期无限膨胀；
- 文件内容就是当天的流水要点（不再重复日期标题），直接是条目列表：

```markdown
- 修复：订单列表分页总数错误。根因：COUNT 子句没去重导致 join 后行数翻倍；修法：改用子查询 COUNT。
- 方案：金额字段统一用分（BIGINT）存储，放弃 DECIMAL——理由：避免浮点精度与展示层换算分歧。
- 遗留：库存扣减尚未加分布式锁，高并发下可能超卖，下轮处理。
```

要点：
- **只记三点**：现象+根因+修法 / 方案+理由 / 遗留+下一步。这是给「未来的你」排查复发问题用的，不是给用户的汇报；
- **append-only**：写错也不改旧条目，新发现另起一行（保留时间线）；
- **读的时机**：重新接手项目、继续上次任务、同类 bug 复发排查时——先 `list_files` 列出
  `.codepal/progress/` 下的日期文件，`read_file_range` 读最近 1~2 个文件（每个文件本来就只有几行）；
- 它**替代**了已失效的归档对话查询：量小（每天几行）、纯文本、随手可读，且永不膨胀。

## `.codepal/table-relations.md` 格式规范（严格遵守，否则无法增量合并/检索）

每张业务表一个小节，二级标题格式固定为 `## 表 <表名>`（检索与定位都依赖它）：

```markdown
## 表 orders（订单表）

- 业务含义：记录用户提交的采购订单，是交易流程的主表
- 关键字段：id、user_id（下单用户）、status（状态：0待支付/1已支付/2已取消）、amount（实付金额）
- 关联关系：user_id → users.id；被 order_items.order_id 引用（一对多）
- 业务规则：取消订单只改 status 不物理删除；金额以分存储避免浮点误差
- 更新时间：2026-09-15
```

要点：
- 标题里带中文含义，正文列**业务含义 / 关键字段 / 关联关系 / 业务规则 / 更新时间** 五要素；
- 关联关系写**双向**：「本表字段 → 对方表.字段」和「被谁引用」都写；
- 业务规则写那些**不查代码不知道**的隐性约定（软删、状态机、金额精度等）；
- 小节内字段按业务重要性排序，不要照抄建表语句。

## 更新纪律（增量合并，绝不整体重写）

- 改某张表 → 用 `read_file_range` 定位它的 `## 表 <表名>` 小节 → `edit_file` **精确替换该小节**
  （search 用小节标题行到下一小节标题行之间的完整文本，必须先读再改）；
- 新表 → 用 `edit_file` 在文件末尾追加新小节（search 匹配文件结尾的最后一行）；
- **绝不用一次大替换重写整个关系文档**——那会覆盖丢失其它表已记录的内容；
- 文档与数据库实际结构冲突时，**以 `query_database` 查到的为准**，同时更新文档。

## 与 query_database 配合（有数据源时的标准动作）

前提：用户已配置数据源（`query_database` 工具描述里会列出可用数据源清单）。
**未配置数据源时，走下一节的代码推断路径**，两者维护的是同一份 `.codepal/table-relations.md`。

1. `mode="data"` 执行 `SHOW TABLES` → 列出所有表，对照关系文档找出**未记录**的表；
2. `mode="schema"` 传 table_name → 拿列结构（列名/类型/键/注释）；
3. `mode="data"` 执行抽样 `SELECT`（自动 LIMIT 10）→ 用真实数据确认字段业务含义与表间关联；
4. MySQL 可直接查外键关系：
   `SELECT TABLE_NAME, COLUMN_NAME, REFERENCED_TABLE_NAME, REFERENCED_COLUMN_NAME FROM information_schema.KEY_COLUMN_USAGE WHERE TABLE_SCHEMA = DATABASE() AND REFERENCED_TABLE_NAME IS NOT NULL;`
5. 查清后**立即回写**关系文档（回到上面"何时写"第 1 条）——调查成果不落文档就等于白查。

## 没有配置数据源时：从实体类与代码推断

数据源未配置（`query_database` 不可用）时，表关系**依然要维护**，只是调查手段换成代码侧、
可信度降级为「推断」：

1. **找实体类**：`search_tool` 搜 `@TableName` / `@Table` / `@Entity` / `extends BaseModel`
   等注解定位表对应的实体类 → `view_file_outline` / `read_file_range` 读字段与注释
   （字段含义以注释为准）；
2. **找关联**：
   - JPA / MyBatis-Plus 注解：`@JoinColumn`、`@ManyToOne`、`@OneToMany`、`@TableField`；
   - Mapper XML 里的 `JOIN ... ON` 与 `resultMap`：**JOIN 条件是最可靠的表间关系来源**；
   - Service 层代码：跨表读写、按外键查询的业务逻辑；
3. **标注可信度**：凡未经数据库验证的条目，在「关联关系」末尾标注
   「（推断自代码，未在库中验证）」，让用户一眼区分事实与推断；
4. **升级为已验证**：之后用户配置了数据源，用 `query_database` 的 schema/外键查询核对——
   一致则去掉「推断」标注，不一致以库为准修正；
5. 同样**只整理当前任务涉及的表**，"初始状态纪律"里禁止全量扫描的约束不变。

## `.codepal/architecture.md` 结构建议

按以下小节组织（没有的小节不写，按项目实际情况取舍）：

- **项目概览**：一句话说清这是个什么系统、服务谁
- **模块结构**：按目录/包列出模块与职责，标注入口
- **技术栈**：语言、框架、数据库、关键三方依赖及选型原因
- **数据模型总览**：核心业务域一段话，细节指向 `.codepal/table-relations.md`
- **进行中与遗留**：当前做到哪、已知问题、下一步（跨会话续接的关键）
- **关键技术决策**：为什么这么设计、放弃了什么方案（这是最容易随会话丢失的知识）

## git 纪律

- **绝不主动**对这些文档执行 `git add` / `git commit` / 推送——是否把文档提交入库**完全由用户决定**；
- 用户明确要求提交时才操作，且只提交用户指定的文件；
- 用户若问"要不要提交/忽略"，可以给建议（如加入 `.gitignore`），但**不擅自修改** `.gitignore`。

## 纪律要点

- **实时优先**：涉及表/架构的发现，当场落文档，不要攒到收尾——攒到收尾必忘；
- **先读后写**：edit_file 的 search 要求精确匹配，天然强制先读；跳过读取盲改必失败；
- **增量合并**：关系文档只动目标小节；架构文档只动对应小节；
- **以库为准**：文档与数据库实际结构冲突时，以 `query_database` 结果为准并同步修正文档；
- **不扫全库**：初始阶段禁止为填充文档而系统性扫描项目（见"初始状态纪律"）；
- **静默执行**：读写文档是内部动作，不必在回复里复述「我更新了文档」（首次创建位置可顺带说明）；
- **防膨胀**：单条小节控制在 10 行内；过时的记录直接更新而非追加历史版本。
